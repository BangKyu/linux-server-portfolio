# DNS Caching Server 정리

## 1. DNS란?

DNS(Domain Name System)는 사람이 기억하기 쉬운 Domain Name을 컴퓨터가 통신에 사용하는 IP 주소로 변환하는 시스템이다.

예:

```text
www.naver.com
        ↓ DNS
223.xxx.xxx.xxx
```

반대로 IP 주소를 Domain Name으로 변환하는 기능도 수행할 수 있다.

인터넷 통신은 IP 주소를 기반으로 이루어지기 때문에 사용자가 Domain Name으로 서버에 접속하려면 DNS를 통한 이름 해석 과정이 필요하다.

---

## 2. DNS가 필요한 이유

사람이 모든 서버의 IP 주소를 기억하기는 어렵다.

예를 들어 다음처럼 IP 주소를 직접 기억하는 대신:

```text
223.xxx.xxx.xxx
```

다음과 같은 Domain Name을 사용한다.

```text
www.naver.com
```

DNS Server가 Domain Name에 해당하는 IP 주소를 찾아 Client에게 알려준다.

```text
Client
  |
  | www.naver.com의 IP 주소는?
  v
DNS Server
  |
  | 223.xxx.xxx.xxx
  v
Client
```

---

## 3. Domain Name의 구조

Domain은 계층적인 구조로 구성된다.

예:

```text
www.naver.com.
```

각 부분의 의미:

```text
.       → Root Domain
com     → Top-Level Domain
naver   → Second-Level Domain
www     → Host Domain
```

구조:

```text
                    .
                    |
                   com
                    |
                  naver
                    |
                   www
```

Domain Name의 가장 마지막에는 원래 Root Domain을 나타내는 `.`이 존재한다.

```text
www.naver.com.
```

일반적으로 사용할 때는 마지막 `.`을 생략한다.

```text
www.naver.com
```

---

## 4. DNS Server의 종류

DNS Server는 역할에 따라 여러 종류로 구분할 수 있다.

### 4-1. Caching Name Server

자신이 특정 Domain을 직접 관리하지 않고 DNS 조회 결과를 Cache에 저장하는 DNS Server이다.

```text
Client
   |
   | DNS Query
   v
Caching DNS Server
   |
   | 필요한 경우 외부 DNS 조회
   v
Internet DNS
```

한 번 조회한 Domain의 정보를 Cache에 저장하기 때문에 동일한 Domain을 다시 요청하면 더 빠르게 응답할 수 있다.

주요 목적:

```text
DNS 조회 결과 Cache
DNS 응답 속도 향상
외부 DNS Query 감소
내부 Client의 공통 DNS Server 역할
```

이번 실습에서 구축한 Server가 해당된다.

```text
192.168.111.100
→ DNS Caching Server
```

---

### 4-2. Primary Name Server

Master DNS Server라고도 한다.

특정 Domain의 실제 DNS 정보를 직접 보관하고 관리한다.

예:

```text
example.com
```

과 같은 Domain에 대해 다음과 같은 정보를 Zone File에 저장할 수 있다.

```text
Domain → IP
Mail Server
Name Server
기타 DNS Record
```

주요 파일:

```text
/etc/named.conf
/var/named/
```

Primary DNS Server는 이후 Master DNS Server 실습에서 다룬다.

---

### 4-3. Secondary Name Server

Slave DNS Server라고도 한다.

Primary DNS Server의 Zone 정보를 복제하여 보관한다.

```text
Primary DNS
     |
     | Zone Transfer
     v
Secondary DNS
```

Primary DNS Server에 장애가 발생했을 때 DNS 서비스를 계속 제공할 수 있도록 구성할 수 있다.

## 5. BIND란?

BIND는 다음의 약자이다.

```text
Berkeley Internet Name Domain
```

Linux에서 DNS Server를 구축할 때 사용하는 DNS Server Software이다.

Rocky Linux에서 사용하는 주요 Package:

```text
bind
bind-utils
bind-libs
```

설치:

```bash
dnf install -y bind bind-utils bind-libs
```

```text

```


## 7. DNS Port

DNS는 기본적으로 Port 53을 사용한다.

```text
TCP 53
UDP 53
```

일반적인 DNS Query는 주로 UDP 53을 사용한다.

필요한 경우 TCP 53도 사용한다.

DNS Server의 Listen 상태 확인:

```bash
ss -luntp | grep ':53'
```

이번 실습에서는 다음 주소에서 `named`가 Listen하는 것을 확인하였다.

```text
192.168.111.100:53/udp
192.168.111.100:53/tcp
127.0.0.1:53/udp
127.0.0.1:53/tcp
```

## 8. DNS 주요 설정 파일

### /etc/named.conf

BIND의 핵심 설정 파일이다.

```text
/etc/named.conf
```

DNS Server가 어떤 Interface에서 요청을 받을지, 어떤 Client의 요청을 허용할지, Recursive Query를 사용할지 등을 설정한다.

---

### /etc/resolv.conf

Linux Client가 사용할 DNS Server의 주소를 확인할 수 있는 파일이다.

```text
/etc/resolv.conf
```

예:

```text
# Generated by NetworkManager
nameserver 192.168.111.2
```

의미:

```text
이 시스템이 DNS Query를 보낼 DNS Server
→ 192.168.111.2
```

이번 실습에서는 Client DNS를 다음과 같이 변경하였다.

```text
기존
192.168.111.2

변경
192.168.111.100
```

---

### /etc/hosts

IP 주소와 Host Name을 로컬 시스템에서 직접 연결할 수 있는 파일이다.

```text
/etc/hosts
```

예:

```text
192.168.111.100 dns-server
```

DNS Server를 조회하지 않고 Local System에 직접 이름과 IP 주소를 등록하는 방식이다.

실습 자료에서는 `/etc/hosts`에 Domain과 IP를 직접 등록하여 DNS Server가 없어도 지정한 이름을 해석하는 동작을 확인하였다.

---

## 9. /etc/hosts와 DNS 차이

### /etc/hosts

Local System에 직접 저장한다.

```text
IP 주소 ↔ Host Name
```

장점:

```text
설정이 간단
DNS Server 없이도 이름 해석 가능
```

단점:

```text
각 Client마다 직접 수정 필요
많은 Host를 관리하기 어려움
IP 변경 시 각 시스템의 파일 수정 필요
```

---

### DNS Server

중앙 DNS Server가 Domain 정보를 관리한다.

```text
Client
   |
   v
DNS Server
   |
   v
IP 주소 반환
```

여러 Client가 동일한 DNS Server를 사용할 수 있기 때문에 중앙 관리가 가능하다.

---

## 10. DNS 이름 해석 기본 흐름

예를 들어 Client가 다음 Domain을 요청한다고 가정한다.

```text
www.naver.com
```

Client가 설정된 DNS Server로 Query를 전달한다.

```text
Client
  |
  | www.naver.com?
  v
DNS Server
  |
  | IP 주소 확인
  v
Client
```

Caching DNS Server에 정보가 없다면 외부 DNS Server에 Query를 수행한다.

```text
Client
   |
   v
Caching DNS Server
   |
   | Cache에 없음
   v
외부 DNS Server
   |
   | IP 주소 응답
   v
Caching DNS Server
   |
   | Cache 저장
   v
Client
```

---

## 11. DNS Cache 동작

Caching DNS Server가 처음 Domain Query를 받으면 Cache에 정보가 없는 경우 외부 DNS Server에 Query한다.

### 첫 번째 Query

```text
Client
   |
   v
Caching DNS
   |
   | Cache Miss
   v
외부 DNS
```

따라서 응답 시간이 상대적으로 길어질 수 있다.

---

### 두 번째 Query

동일한 Domain을 다시 요청하면 이전 Query 결과가 Cache에 존재할 수 있다.

```text
Client
   |
   v
Caching DNS
   |
   | Cache Hit
   v
Client
```

외부 DNS Server에 다시 Query하지 않고 Cache의 정보를 이용할 수 있기 때문에 빠르게 응답할 수 있다.

---

## 12. 실습에서 확인한 Cache 효과

먼저 DNS Cache를 초기화하였다.

```bash
rndc flush
```

첫 번째 Query:

```bash
dig @192.168.111.100 www.naver.com | grep -E 'status:|Query time|SERVER:'
```

결과:

```text
status: NOERROR
Query time: 2128 msec
SERVER: 192.168.111.100#53
```

두 번째 동일 Query:

```bash
dig @192.168.111.100 www.naver.com | grep -E 'status:|Query time|SERVER:'
```

결과:

```text
status: NOERROR
Query time: 2 msec
SERVER: 192.168.111.100#53
```

비교:

```text
첫 번째 Query
2128 msec

두 번째 Query
2 msec
```

두 번째 Query가 매우 빠르게 처리되는 것을 통해 DNS Cache가 동작하고 있음을 확인하였다.

## 13. rndc

`rndc`는 다음의 약자이다.

```text
Remote Name Daemon Control
```

실행 중인 `named`를 관리할 수 있는 명령어이다.

쉽게 표현하면:

```text
named
→ 실제 DNS 요청을 처리하는 DNS Server Daemon

rndc
→ 실행 중인 named를 관리하는 명령어
```

예:

```bash
rndc flush
```

DNS Cache를 삭제한다.

Service 전체를 재시작하지 않고 Cache를 초기화할 수 있다.

---

## 14. dig

`dig`는 DNS 정보를 조회하는 명령어이다.

특정 DNS Server를 지정하지 않고 조회:

```bash
dig www.naver.com
```

특정 DNS Server를 지정:

```bash
dig @192.168.111.100 www.naver.com
```

의미:

```text
192.168.111.100 DNS Server에게
www.naver.com 정보를 직접 질문
```

---

## 15. dig 주요 출력

예:

```text
;; ->>HEADER<<- opcode: QUERY, status: NOERROR

;; Query time: 2 msec

;; SERVER: 192.168.111.100#53
```

### status: NOERROR

```text
DNS Query가 정상적으로 처리됨
```

### Query time

```text
DNS 응답에 걸린 시간
```

### SERVER

```text
Query에 응답한 DNS Server
```

이번 실습:

```text
SERVER: 192.168.111.100#53
```

따라서 우리가 구축한 Local DNS Server가 응답했음을 확인할 수 있다.

## 17. named.conf 기본 설정

BIND 설치 직후 주요 설정은 다음과 같았다.

```conf
listen-on port 53 { 127.0.0.1; };
listen-on-v6 port 53 { ::1; };

allow-query { localhost; };

recursion yes;

dnssec-validation yes;
```

이 상태에서는 기본적으로 Localhost 중심으로 DNS 요청을 처리한다.

내부 Client에서도 DNS Server를 사용하려면 설정 변경이 필요하다.

---

## 18. Caching DNS Server 설정

실습에서 사용한 주요 설정:

```conf
listen-on port 53 { any; };
listen-on-v6 port 53 { none; };

allow-query     { localhost; 192.168.111.0/24; };
allow-recursion { localhost; 192.168.111.0/24; };

recursion yes;

dnssec-validation yes;
```

---

## 19. listen-on

```conf
listen-on port 53 { any; };
```

DNS Server가 IPv4 Interface에서 DNS 요청을 받을 수 있도록 설정한다.

기본값:

```conf
listen-on port 53 { 127.0.0.1; };
```

이면 Localhost에서만 요청을 받을 수 있다.

실습에서는:

```conf
listen-on port 53 { any; };
```

로 변경하여 `192.168.111.100` Interface에서도 DNS 요청을 받을 수 있도록 하였다.

---

## 20. listen-on-v6

```conf
listen-on-v6 port 53 { none; };
```

이번 실습에서는 IPv4 DNS 환경만 사용하므로 IPv6 DNS Listen을 사용하지 않도록 설정하였다.

---

## 21. allow-query

```conf
allow-query { localhost; 192.168.111.0/24; };
```

DNS Query를 허용할 Client 범위를 설정한다.

이번 설정:

```text
localhost
192.168.111.0/24
```

즉 Server 자신과 내부 Network의 Client가 DNS Query를 보낼 수 있다.

---

## 22. allow-recursion

```conf
allow-recursion { localhost; 192.168.111.0/24; };
```

Recursive DNS Query를 사용할 수 있는 Client 범위를 지정한다.

이번 실습에서는 내부 Network만 Recursive DNS 기능을 사용할 수 있도록 제한하였다.

```text
192.168.111.0/24
```

---

## 23. recursion

```conf
recursion yes;
```

Recursive DNS Query를 허용한다.

Caching DNS Server는 자신이 관리하지 않는 Domain의 정보를 다른 DNS Server에 Query하여 Client에게 결과를 반환해야 하므로 Recursive Query가 필요하다.

```text
Client
   |
   v
Caching DNS
   |
   | Recursive Query
   v
다른 DNS Server
```

---

## 24. Recursive DNS Server 접근 제어

Recursive DNS Server를 불필요하게 모든 Network에 공개하지 않는 것이 중요하다.

이번 실습에서는:

```conf
allow-query {
    localhost;
    192.168.111.0/24;
};

allow-recursion {
    localhost;
    192.168.111.0/24;
};
```

와 같이 내부 Network만 허용하였다.

구조:

```text
192.168.111.0/24
        |
        | 허용
        v
192.168.111.100
Caching DNS
```

## 25. dnssec-validation

```conf
dnssec-validation yes;
```

DNSSEC 검증 설정이다.

이번 실습에서는 BIND의 기본 설정인 `yes`를 유지하였다.

Caching DNS의 핵심 실습 항목은 다음과 같다.

```text
listen-on
allow-query
allow-recursion
recursion
```

## 32. Cache Hit / Cache Miss

### Cache Miss

Caching DNS Server에 필요한 정보가 없는 상태이다.

```text
Cache
→ 정보 없음
```

외부 DNS Query가 필요하다.

---

### Cache Hit

필요한 DNS 정보가 Cache에 존재하는 상태이다.

```text
Cache
→ 정보 있음
```

외부 DNS Query 없이 저장된 정보를 이용해 응답할 수 있다.

이번 실습의 Query Time 차이:

```text
첫 번째 Query : 2128 msec
두 번째 Query : 2 msec
```

를 통해 Cache 사용 효과를 확인하였다.

---

## 33. TTL과 DNS Cache

DNS Record에는 Cache를 유지할 수 있는 시간이 존재한다.

이를 TTL(Time To Live)이라고 한다.

```text
TTL
→ DNS 정보를 Cache에 보관할 수 있는 시간
```

TTL이 만료되면 DNS Server는 필요한 경우 다시 외부 DNS Query를 수행한다.

따라서 DNS Cache의 정보가 영구적으로 저장되는 것은 아니다.

## 34. IPv6 관련 Log

`named`를 실행했을 때 다음과 같은 Log가 확인되었다.

```text
network unreachable resolving './NS/IN': IPv6주소#53
network unreachable resolving './DNSKEY/IN': IPv6주소#53
```

현재 실습 환경에서 외부 IPv6 Route를 사용할 수 없어 IPv6 DNS Server로 접근하지 못해 발생한 메시지였다.

하지만 이후:

```text
all zones loaded
running
```

이 출력되었고:

```text
Active: active (running)
```

상태를 확인하였다.

또한 IPv4 DNS Query도 정상적으로 동작하였다.

따라서 이번 IPv4 기반 Caching DNS 실습에는 문제가 없었다.

## 35. DNS Server 정상 동작 확인 방법

Caching DNS Server 구축 후 다음 순서로 점검할 수 있다.

```text
1. BIND Package 설치 확인

2. /etc/named.conf 설정 확인

3. named-checkconf 문법 검사

4. Firewall DNS 허용 확인

5. named Service 상태 확인

6. TCP/UDP 53 Port 확인

7. Server 자체 DNS Query 확인

8. Cache 초기화

9. 동일 Domain 반복 Query

10. Query Time 비교

11. Client DNS를 Local DNS Server로 변경

12. Client에서 nslookup 확인
```

```bash
named-checkconf
```

### Service 시작

```bash
systemctl enable --now named
```

### Service 상태

```bash
systemctl status named
```

```bash
ss -luntp | grep ':53'
```

```bash
firewall-cmd --permanent --add-service=dns
firewall-cmd --reload
firewall-cmd --list-services
```

```bash
rndc flush
```

### DNS Query

```bash
dig @192.168.111.100 www.naver.com
```

```bash
dig @192.168.111.100 www.naver.com | grep -E 'status:|Query time|SERVER:'
```


## 38. 이번 실습 핵심

이번 실습에서 가장 중요한 흐름:

```text
Client
  |
  | DNS Query
  v
192.168.111.100
DNS Caching Server
  |
  | Cache Miss
  v
외부 DNS Query
  |
  v
결과 Cache 저장
  |
  v
Client 응답
```

동일 Domain을 다시 조회하면:

```text
Client
  |
  v
192.168.111.100
  |
  | Cache Hit
  v
빠른 DNS 응답
```

실제 확인 결과:

```text
첫 조회
2128 msec

두 번째 조회
2 msec
```

따라서 BIND를 이용하여 내부 Client가 사용할 DNS Caching Server를 구축하고, 반복 Query의 응답 시간을 비교하여 Cache가 실제로 동작하는 것을 확인하였다.
